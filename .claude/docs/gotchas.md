- **A CSS animation starts on the frame AFTER its class lands, so a setTimeout that thinks it knows the animation's clock is wrong at BOTH ends** (learned on the lb counter's number swap, 2026-08-01; measured slop ~2 frames, ~35ms). Two distinct failures from the one cause: a cleanup timer sized to the animation's own duration fires EARLY and cuts the last ~15% — it snapped the settle right where an ease-out is finest. And an animation given its full time slot is still ~2 frames from done when the next step fires, so it gets CANCELLED at ~92% — a pop exactly where an ease-in moves fastest. **The fixes are different and both are needed:** clean up on the element's own `animationend` (with a generous timeout ONLY as the fallback for a tab hidden mid-gesture, where animations freeze and the event never fires — the hazard that killed the LAND flourish); and where a stage must hand off at a fixed beat, give it a DURATION SHORTER THAN ITS SLOT and let `both` hold the landed state until the cut. Applies to any timed multi-stage gesture, not just this one — check `animationstart`/`animationend`/`animationcancel` pairs before believing a chained animation is clean, because a `cancel` in that log is a visible pop nobody screenshots. **And a chained beat whose predecessor's length VARIES with content must be derived from that length, not from a constant** — the contact send fired on a hardcoded delay and finished 200ms before the letter it was supposed to follow, because the message's decode runs longer with more boards in the deck; `bdmApply` now returns the arrival's real duration and the send waits on it.
- **Anything centred whose text changes width will drag its static neighbours** — the reflow reads as motion, and worse, two lines at different font sizes drag by different amounts and read as uncoordinated. Reserve the slot (`min-width` + `text-align: center`) rather than pinning the neighbours. In the monospace label font `1ch` is the digit advance, but CSS adds a letter-space after EVERY character including the last, so N characters occupy N×(1ch + tracking) — a slot sized `2ch` alone is short by the tracking and still jumps.

- **A child of a `display:none` parent never renders, whatever its own CSS says** (2026-08-06, cost a debugging cycle on the mobile header). The drop's markup lived inside `.nbar`, which is `display:none` below 941px — so on a phone the menu opened, set every class, reported `visibility: visible` and a real `getBoundingClientRect`, and painted **nothing**. Every signal said working. - **GitHub Pages sends `Cache-Control: max-age=600` and supports NO custom headers** — no `_headers`, no `.htaccess`, nothing. Combined with iOS having no shift-reload (its only hammer is Settings → Safari → Clear History, which signs you out of everything), a phone can sit on a stale build with no way out. **Do not fight the cache — sidestep it:** `redesign/bar.html` is a loader that never changes (so caching it is fine, even good) and forwards to `bar-lab.html?v=<Date.now()>`, a URL neither the CDN nor the phone has seen. `replace()` not `assign()`, so a back press leaves instead of bouncing through the loader. **And put a BUILD STAMP on any page being judged from a phone** — it is the only way the device can answer "am I even looking at the new file" without a second machine. Bump it every push. Second, separate trap: **a stored `localStorage` pick outranks a new default**, so changing a default and loading a genuinely fresh build still shows the old value — indistinguishable from cache. Ship a RESET that also sweeps retired keys.

- **An EVEN-height box percentage-centred in an ODD-height container straddles a half-pixel, and at DPR 1 that paints a soft antialiased row on BOTH edges** (Dylan spotted it on the bay-close chip, 2026-08-01: "does the top of the black box have a couple extra rows of pixels compared to the bottom?"). The layout can be provably symmetric and it will still read a row taller and fuzzier than it is — measure before hunting a centring bug that isn't there. Sibling elements can disagree for pure parity reasons: the bay's 5px mid dot is crisp on the same `.5` centre precisely because 5 is ODD. **Fix is `top: round(50%, 1px)` with a bare `top: 50%` ahead of it as the fallback** — snapping the offset to the pixel grid works at any container parity, which picking a fixed odd or even height cannot, since these containers are viewport-driven and change parity as the window resizes (the bay panel is 811px at 1440×900 and 812 at 1440×901; verified crisp at both). Note this is a DPR-1 problem: on a retina display a `.5` CSS px is a whole device pixel and nothing shows, so an external monitor will surface it when the laptop panel does not. Same family as the flush-edges gotcha below — sub-pixel geometry, not colour.
- **A sub-pixel "snap" transform can CAUSE the blur it was written to fix — measure before you correct sub-pixel geometry** (2026-08-04, the contact composer, DPR 1, pixel audit of the sealed envelope). A previous pass translated the box by a fraction to park a fractional layout origin on the whole-px grid. With it, the 3px silhouette rendered 55% / 100% / 100% / 41% across FOUR device rows and every 1px crease came out as a grey PAIR; with `transform: none` and nothing else changed, three whole rows and one solid row. Chrome already snaps that subtree's PAINT, so an explicit fractional transform is honoured ON TOP of the snap — you are adding the straddle you meant to remove. It looked half-right for a while because the X offset happened to be 0 at one width. **What actually delivers crispness: an integer box SIZE, .5-centred coordinates, and ODD stroke widths — no transform.** Corollary: a box whose lines must stay crisp should carry no transform at all, so presses and shakes there ride the independent `scale`/`translate` properties instead (see `.bdm-prev`). Sample device rows off a real screenshot before believing either story — this is the same family as the parity gotchas above, opposite conclusion.
- **A hover must never move its own hit box off the cursor, and decorative furniture must never hit-test** (2026-08-06, Dylan's spazz catch: park the cursor on a card edge or a bar organ's dot line and the hover looped enter/leave at 12–28Hz — measured 30 and 69 cycles per 2.5s). Two mechanisms, one law: `.scard`'s hover lift (−4px) carried the box up off the parked cursor (fixed by an invisible hover-only apron under `.d7f` covering the vacated strip — the drawn-extent hit law read in REVERSE: the rest box is the promise; also covers `.bay-item`'s −3px); and the bar's dot pull slid a `.bardot` under the cursor, stealing the organ's hit (fixed: `pointer-events: none` — dots are furniture). Scale-UP hovers self-latch (the box grows around the cursor) and need nothing — only move-away/shrink hovers loop. Diagnose with parked-pointer event counters and a rect trap fired at the boundary event — screenshots can't see it.
- **`repeat(auto-fit, minmax(N, 1fr))` counts the GAPS, and going one pixel over silently drops a column** (bit on the composer's four-field row). The fit test is `N × cols + gap × (cols − 1) ≤ available`, so four 140px minimums with three 11px gaps needed 593px of a 580px tray and quietly reflowed to two rows — which then ate the height of everything below it. There is no warning; the layout just changes shape. When a wrap would be expensive, do the arithmetic against the real inner width (tray padding and border included) rather than eyeballing the minimum.
- **To make a wrapper's children participate in an ANCESTOR's grid, give the wrapper `display: contents`** — it keeps existing as a DOM node (so JS lookups, data attributes, delegated listeners and per-node bookkeeping all still work) but stops being a box, and its children become grid items of the grid above. This is what lets the composer's letter put every line's tag, dot and body into three aligned columns; a wrapper box would make each line its own one-row grid and nothing would line up between rows. **Two consequences to plan for:** the wrapper's own box properties die with it (a `min-height` holding a row open has to move to a child — and a grid item is BLOCKIFIED, so `min-height` works there even if the child's own `display` is `inline`), and a `::before`/`::after` on a child is NOT a substitute for a real element, because the pseudo lives inside that child's box rather than becoming a sibling grid item.
- **A jokey or example value in a field that SENDS somewhere must be a CSS pseudo-element, never text** — `::before { content: … }` cannot be reached by `textContent`, so it can never be selected, copied, or serialised into the outgoing message, and it disappears the moment a real value is typed (`:empty`). The composer's goofy per-board hints ("ill give ya bout $3.50") ride this: as real content, one distracted visitor mails that to an actual person. Applies to any placeholder-ish flourish on a form that has a destination, not just this one.
- **Redefining a custom property on a subtree re-points every `calc()` inside it in one declaration** — the composer caps its furniture scale with `.bdm-form, .bdm-actions { --envk: var(--trayk) }`, so all ~15 `calc(Npx * var(--envk))` values in those subtrees switch to the capped scale at once, with nothing to miss and nothing to keep in sync. **You cannot self-reference** (`--envk: min(var(--envk), 1.1)` is a cycle and resolves to the guaranteed-invalid value), so the cap has to arrive as a SECOND variable set further up. Good shape whenever one subtree needs a different scale from its siblings.
- **`clearInterval(h)` does not falsify `h`** — if a timer handle doubles as "something owns this element right now", NULL it when the work lands. `decodeEl` cleared but kept its id on `el._dt`, so every element that had ever decoded read as permanently mid-decode; any guard written against it silently never fired. Cost a real bug on the send button's destination (a per-keystroke plain write fighting the scramble that was already running).

## A sticky child's stick-room is the parent's CONTENT box (2026-08-14)

The scroll relay's runway was first built as `padding-bottom` on the section — the sticky `.secbody` computed `position:sticky; top:64px` correctly and NEVER pinned, silently. The room a sticky element has to offset is its containing block's CONTENT box; padding is outside it, so a body that fills the content box exactly has zero stick range. And the obvious second try — `margin-bottom` on the sticky child — fails too: with no parent padding/border below, the child's bottom margin COLLAPSES THROUGH the parent's edge and escapes. THE FIX: a real spacer element (`<i class="runway">`) inside the section after the body — real in-flow height inside the content box. THE TELL: computed style says sticky with the right top, but a mid-scroll gBCR shows the "pinned" element riding past the pin line at scroll speed.

## A `const` arrow called at boot is a TDZ landmine — and it kills the WHOLE script (2026-08-16)

`stackDealtAway()` called `dockActive()` — a `const` arrow declared ~2500 lines BELOW it — and `renderPicks` runs at boot via `lisstTab()`. `const`/`let` do not hoist like function declarations, so that call threw `ReferenceError: Cannot access 'dockActive' before initialization`, which **aborted the entire inline script mid-boot**: every declaration after that point stayed uninitialised for the life of the page. THE SYMPTOM WAS 5000 LINES FROM THE CAUSE — every route threw `Cannot access 'caseOpen' before initialization` (a `let` that never got to run), the picks page rendered nothing, and the stack came back empty. Same shape as the 2026-08-12 `piconPoked` bite. THE FIX: term order — `stackDealt && onPicks && dockActive()`, so the boot render short-circuits before reaching it, with a comment saying not to tidy the terms. THE TELL: a TDZ error naming a variable you did not touch, plus large unrelated parts of the page silently not working.

## Syntax-check the inline script before verifying anything (2026-08-16)

A comment added inside the CSS/JS ran past the block's own `*/` and became bare JavaScript — a syntax error that killed the whole file, with the browser console showing nothing useful. Two verification rounds were wasted chasing "logic" that never ran. THE HABIT, cheap and worth doing before every browser check:

```
node -e "const fs=require('fs');const h=fs.readFileSync('redesign/k-home-dual.html','utf8');
const re=/<script(?![^>]*\bsrc=)[^>]*>([\s\S]*?)<\/script>/g;let m,i=0,bad=0;
while((m=re.exec(h))){i++;try{new Function(m[1]);}catch(e){bad++;console.log('#'+i+': '+e.message);}}
console.log(bad?'':'all '+i+' inline scripts parse clean');"
```

It catches parse errors only — the TDZ bite above is a RUNTIME error and needs the boot-error collector instead: navigate with `initScript` = `window.__boot=[];addEventListener('error',e=>window.__boot.push(e.message))`, then read `window.__boot`.

## `--tbh` is a boot-time snapshot of a bar whose height can change (2026-08-16)

`setTbh()` writes `.topbar.offsetHeight` once at boot. The phone bar's height is driven by its tallest child — the picks stack — so emptying the stack collapsed the bar 84 → 60px while `--tbh` stayed 84, stranding everything pinned to it 24px low. Fixed by making the stack reserve its height (`.hpicks { min-height }`), not by re-measuring. **Anything that changes a bar child's height must either reserve the space or re-run `setTbh`** — and note `setTbh` is not wired to the resize handler either, so a programmatic resize leaves `--tbh` stale (real phones never resize, which is why this only bites in Chrome).

## Fractional strokes on UNSCALED furniture render jagged at DPR 3 (2026-08-16)

The offer box's 2.5px border + 1.25px pseudo offsets = 7.5 / 3.75 DEVICE pixels on the phone — the gradient-drawn rails AA'd fuzzy against the browser-snapped border and every corner stepped (Dylan: "jagged corners like our half pixel render rounding errors from before"). THE FIX: whole-CSS-pixel everything — border 3, rails 3, pseudo offsets -1/-3, label -1.5 (the knob pair re-derived; the in-file comment says how). THE SCOPE RULE: this applies to UNSCALED furniture only — the cards' own fractional strokes (4.31cqw etc.) live inside lockCardScale's continuous transform, where everything blurs together or not at all; furniture that rides BESIDE the scaled card (the offer/message boxes) plays by whole-pixel rules. Same family as the DPR-1 parity gotchas, third variant: spec-vs-snapped at DPR 3.

## Inline SMIL: the clock is the document's, and only inline is controllable (2026-08-16)

The drawn logo's `begin="0.45s"` counts from DOCUMENT LOAD on a wall clock that keeps running while the SVG's ancestors are `display:none` — boot on a collection page and the draw is long finished before the first visit home. `svgEl.setCurrentTime(0)` REWINDS the whole timeline (begins re-fire), which is what turns a load beat into an ARRIVAL beat (route's home branch calls it every visit; reduced motion jumps PAST the end instead — fill=freeze holds the finished mark). TWO PACKAGING TRAPS: an `<img src=*.svg>` runs SMIL but exposes NO timeline control (setCurrentTime needs the inline element), and an inline SVG's internal `<style>` is DOCUMENT-GLOBAL — the logo's `.ink` class was one hostile rename away from styling someone else's markup; its props moved to page CSS scoped under the svg's id, title/desc ids namespaced for the same reason.

## A fixed element's bottom is the LAYOUT viewport — iOS paints page content behind the floating toolbar (2026-08-16)

The intro's full-screen veil (`position:fixed; inset:0`-style) verified clean in the pane and showed a band of RAW PAGE at the bottom of the 15 Pro sim: fixed boxes end at the layout viewport's bottom, and iOS Safari happily paints the document in the bezel band behind/around the floating URL pill. Anything meant to COVER the screen needs bottom overscan (the veil carries `bottom: -160px`; a translateY exit in % rides the taller box and still clears). Same family as the round-7 "html painted white" hardening and the dvh case anchor — the layout viewport is not the glass.

**AMENDED 2026-08-16 (his real-phone screenshot): overscan is NOT a guarantee — how far past the layout viewport a device actually paints a fixed box is the device's business.** The −160 veil verified clean on the iOS 27 sim and his glass still showed collection tiles behind the address pill during the intro's opaque phase. When a cover MUST be total, don't fight the viewport model — **empty the band at the source**: the intro holds the page below the masthead at `visibility: hidden` until the shrink beat (`body.intro:not(.intro-shrink) .spine > :not(.masthead)`), so whatever the device paints down there is blank html ground. A fixed cover is a costume; content-hiding is a fact.

## WebKit paints a round line-cap at zero dash progress (2026-08-16)

A path armed for stroke-draw (`stroke-dasharray: 1; stroke-dashoffset: 1` — nothing drawn yet) with `stroke-linecap: round` renders its START CAP as a dot in WebKit before the draw begins. The drawn logo's two circle arcs each park a ~1px speck near the anchor dots at rest scale — invisible — but the load intro scales the logo ~2.4× and the specks read as two stray dots during the big draw's first seconds (sim-caught; Dylan caught it on glass). **FIXED 2026-08-16: every animated path carries `opacity="0"` + an SMIL `<set to="1" begin=<its draw begin> fill="freeze"/>`** — nothing exists before its pen touches down, the set re-fires on the rewind, and freeze survives reduced-motion's jump-past-end. The pattern is the fix for any future stroke-draw art with round caps.

## The pane's rAF wedge came back — design ceremony pumps on timeouts (2026-08-16)

Reconfirmed live: `requestAnimationFrame` never fires in the pane again (probe: rAF vs 600ms timeout race → timeout wins; the 2026-08-03 amendment's "runs again" is dead again — PROBE FIRST remains the law). Consequence baked into thread 3: any multi-beat ceremony that must SURVIVE a frozen frame loop (background-tab loads freeze rAF on real phones too) drives its sequencing on setTimeout and its transition kicks on the reflow idiom (`void el.offsetWidth`), reserving rAF for per-frame VISUAL work only (glide's scroll writes). The select ceremony, the intro walk and the rider all run to completion under a dead frame loop; only their pixels freeze.

## A lazy image with no intrinsic size is a 0×0 box — and a zero box never lazy-loads (2026-08-16)

The ONE CARD SPEC's stage img is absolute + auto-sized (`inset:0; margin:auto; max-height/max-width`) — before load it has no intrinsic dimensions, so it computes 0×0; a zero box never intersects the viewport, so `loading="lazy"` NEVER FIRES. Permanent chicken-and-egg, masked by the cache: Chromium/WebKit load an already-cached URL immediately regardless, so the image "works" whenever the same file is warm from elsewhere on the page — which is how the header minis showed boards ONLY on their own collection's page (Dylan's catch: "a routed board turns to a blank mini in the hand shaped section"). THE LAW: any template render that is chrome or flight — on screen by definition — must EAGER its imgs (`renderPicks` + `buildFly` do, post-innerHTML `img.loading = "eager"`), and clipped/scaled seats should give the img an explicit pre-load box (`.hpick .d7f .stage img { width/height/object-fit }`). Grid renders keep lazy — their boxes are real (the stage's aspect-ratio) … but note it is the IMG's box that gates, not the stage's, so the grid works only because in-view stages get scrolled through. If a new surface shows cold template cards, check this first.

## A state's `transition` REPLACES the base list — a dropped property snaps (2026-08-16)

`.fveil.on` carried its own shorter `transition` (to dodge a visibility delay) and that list REPLACES the base declaration's — so while `.on` held, `transform` had NO transition and the veil's top-down reveal SNAPPED in one frame on every real device (Dylan's "weird pop… flash a frame"; the pane's frozen transitions could never show it, and the flash frame itself photographed as torn fonts/blank images via iPhone Mirroring's video stream). THE LAW: one transition list on the base rule, states only flip VALUES — and if some property must not transition, handle it in JS (fveil.clear() snaps under `transition: none` + reflow) rather than forking per-state lists that will drift.

## IntersectionObserver never delivers in the pane — the ResizeObserver law's sibling (2026-08-16)

The mobile dims decode (IO-armed, fires as cards scroll into view) never fired in the pane — scrolls, waits, nothing; the same build decoded instantly on the sim and in real headless Chrome. Intersections are computed in the rendering steps, and the pane's frame loop is dead (the rAF wedge), so IO callbacks starve exactly like ResizeObserver's. **Anything IO-gated verifies on the sim or real Chrome only**; in the pane you can prove the observer ARMED (code state) but never that it FIRES. Third member of the family: rAF, RO, IO — if it rides the render loop, the pane can't run it. Related: the picks-deal ceremony also can't complete in the pane (its card flights are bayFlight/glide, rAF per-frame work) — always sim-verify it; don't mistake its pane stall for a regression. **FOURTH MEMBER — THE DECK DRAWER CANNOT BE OPENED IN THE PANE (2026-08-20, found while measuring it for the Figma kit):** `openBay()` / `shopRoom(true)` run fine and their classes land, but `bayP` is advanced by the rAF poser, so the case never leaves its parked off-screen x and EVERY geometry read comes back with the CLOSED numbers. It reads as "the click didn't register" and is nothing of the kind — don't go hunting the click machine. Also note the drawer has no single toggle you can reach from a probe: the deck mark is wired elsewhere, and the reliable opener is a plain `click` on `#bay-panel` (its handler calls `openBay()` whenever `bayP < 1`). In chrome-devtools MCP that click opens it in ~2s and the bay settles on `bay inked locked pulled fullish shadowed`.

## The port repointed every asset path — old muscle memory writes dead links

The copy rewrote six path forms, and a hunk carried over from a vault diff (or a habit from the vault's file) will reintroduce the broken one silently — a missing image just doesn't paint.

| `../site/…` | `site/…` |
| `media/…` | `site/media/…` |

## The canva batch here is a SUBSET — 66 of the vault's 168

`site/img/cards/canva/` ships only the files the live `CANVA` map actually points at (one top + one bottom per board). The vault's `redesign/card-lab/canva/` holds the whole batch, review pages and all. **So a new board's card art is never already here** — adding one means either exporting the pair out of the vault's batch or running the canva flow for it, then dropping the two files in and mapping them. Same for `cuts/` (the six originals cutouts). If a card renders with no artwork, check the file exists before debugging the map.

## `sources/` ordering IS board identity — inserting a photo re-ids everything after it

`build_site.py` assigns ids **positionally**: it sorts each collection folder and numbers what it finds, so `classic-01` is simply the first sorted pair. Nothing in `sources/` records an id — the filename order IS the id. And the `CANVA` card-art map (plus `INVREF`, `DIMS_MM`, and every other hand-kept map in `index.html`) is keyed to those ids.

**Consequence: dropping a new photo in that sorts EARLIER than existing files shifts every id after it by one, and silently unmaps their card art, refs and dims** — the boards keep rendering, wearing each other's artwork. Nothing errors.

**THE LAW: add new boards so they sort LAST** (the existing naming already does this — keep the convention when adding). If a board genuinely has to land mid-order, re-map `CANVA` and the sibling maps in the same pass, and diff `site/data.js` before and after to see exactly which ids moved. Note the inventory refs are non-contiguous on purpose (`classic-01` is CL 3), so the ref number cannot be used to sanity-check the ordinal — it is derived from the map, not from position.

**THE ORIGINALS CARRY ORDERING PREFIXES (2026-08-22).** `sources/originals/` board
folders are named `NN-slug` (`01-og-orange-piro` … `07-bluepiro`). The number pins the
slot; `prettify()` in `build_site.py` strips a leading `\d+[-_]` so it never reaches the
display name. **Adding an original is now just "next number"** — no thinking about where
the name falls alphabetically, no remapping. This was landed as a provable no-op: the six
existing folders were prefixed in their already-sorted order and `site/data.js` came out
**byte-identical**, so `originals-01`…`06` (and the `cuts/originals-0N-1-cut.png` files

`INVREF` and `DIMS_MM`, and their `#01`-style refs are computed at render time from the

## Two sessions cannot share the chrome-devtools MCP profile — bring your own Chrome (2026-08-16)

When two sessions verify at once, the chrome-devtools MCP's one fixed profile becomes a tug-of-war ("browser is already running" on every second call) — and pkilling through it kills the OTHER session's verification. THE ESCAPE: launch a PRIVATE headless Chrome (`--headless=new --remote-debugging-port=<own port> --user-data-dir=<scratchpad>/chrome-x`) and drive it with a ~40-line node CDP script — node ≥22 has WebSocket built in (`fetch /json/list → new WebSocket(target) → Runtime.evaluate {awaitPromise, returnByValue}`), zero dependencies, full rAF/IO/localStorage support — everything the pane can't do. Both A/B ports verified this way.

## Verification traps from the A/B run (2026-08-16)

- **`getComputedStyle` returns a LIVE object — capture values BEFORE mutating class state in a probe.** A check read `cs.color` after `classList.remove(...)` and "proved" CSS dead that was fine. Copy primitives out at read time, then mutate.
- **Chrome won't shrink its window below ~500px** — a resize to 393 lands at innerWidth 500, so "phone" checks in real Chrome run at 500×N. Fine for structure/geometry ratios; exact phone pixels are the sim's job.
- **A synthetic click on a just-re-rendered node is a click on a DETACHED node.** Grabbing an element and clicking it in one eval across a render boundary hits the node the re-render replaced — handlers gone, nothing happens. Re-query at click time after any render boundary.

## A second headless Chrome on a taken --remote-debugging-port SILENTLY SHARES it (2026-08-21)

Two parallel verification harnesses each launched "their own" headless Chrome — private profiles, but the same `--remote-debugging-port=9333`. The second launch does not fail: CDP calls just land on whichever instance owns the port, so probes return ANOTHER page's state (caught red-handed: a `Runtime.evaluate` returned a `location.search` for a URL that harness never requested; `/json/list` showed the live target was the sibling agent's server). The resulting anomalies look exactly like page bugs — wandering rects, one-off empty reads, a variant that "didn't arm" — and none of them were. The private-profile rule from the earlier escape is NOT enough: **parallel harnesses need private PORTS**, and on any anomaly the first check is `/json/list` to confirm who you're actually talking to. Same session, same lesson smaller: parallel agents also share the session scratchpad — namespace harness files per agent (`scratchpad/t1/`, `scratchpad/t2/`) or they overwrite each other.

## Safari cannot be trusted with an ANIMATED filter: drop-shadow — static is fine (2026-08-28, T7)

The lb board shadow rendered in Safari (Mac + iPhone) as a huge jagged gray blob, and on desktop stayed wrong after a hover ended. Root cause chased across headless WebKit trunk, headful WebKit, and the iOS 27 sim: **every static drop-shadow render was clean in all of them** — the corruption lives only in Safari's compositor-animated filter path (documented upstream: stochastic first-paint/partial-repaint corruption that can freeze without finalizing — the sticky half; see mdn/browser-compat-data#17726, WebKit bugs 80323/81263/93471 family). Every route to the blob ran through a filter TRANSITION: the phone dress's .8s blift deepen, the desktop hover's .94s, and the .3s ease-back the sun's release re-arms. THE FIX (in the fv3 lb CSS, "SAFARI'S SHADOW SNAPS"): a WebKit-only block drops `filter` from those three transitions so the shadow steps between states — every state Safari paints is static. Two reusable pieces:
- **The WebKit-only CSS gate is `@supports (background: -webkit-named-image(i))`** — verified true in WebKit, false in Chromium (so Chrome is untouched by construction; the post-fix Chrome phone screenshot came back byte-identical to pre-fix). `@supports (-webkit-touch-callout: none)` is iOS-ONLY — it misses Mac Safari; don't reach for it when both surfaces hurt.
- **A cascade find while placing it:** the `.panel:hover` grow rule (five classes with the pseudo) OUTRANKS `.suntrack`'s `transition-property: none` (four) — so shipped Chrome always ran the sun's per-frame writes THROUGH the .94s transitions while the cursor was on the panel; the mute only wins during the off-panel drain. That's shipped behavior (per-frame retargeting just reads as extra smoothing) — replicated, not fixed, per the bench's quirk law.
If a future animated filter is wanted in Safari anyway, expect to build the shadow as a real element instead (the duplicate-element workaround upstream threads converge on).
